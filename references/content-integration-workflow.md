# 批量内容整合工作流 v2.1（2026-09-05 实战终版）

> 从大量蒸馏拆解整合为主题知识手册的完整流程。629 本 → 12 主章 + 4 专题 · 93 万字符全流程验证（初写 → A/B 拆半 → 合并 → 统稿 → 深补 → 专题切片，2026-09-04/05）。
> 取代旧版（3 并发直读全文模式——实测在 50+ 本主题上必超时/偷懒）。

## 适用场景

- 蒸馏拆解 → 主题化知识手册（本 skill 主场景）
- 博客文章 → 分类知识库
- 会议记录 → 部门知识手册
- 任何「大量零散长文件 → 少量结构化章节」的整合任务

## 核心架构：三层流水线 + 二轮加工

```
蒸馏拆解（真相源，不动）          629 本 × 41KB = 27MB
    ↓ Phase 1 脚本抽取
原料包（.mat.md，中转层）        629 本 × 9KB = 5.6MB   ← 只喂给子代理
    ↓ Phase 2-5 初写（可 A/B 拆半+合并）
主题章节 v1
    ↓ Phase 6 二轮加工（统稿 / 深补 / 专题切片）
主题章节 v2（终稿）              16 章 · 93 万字符实测
```

**为什么必须抽原料包**：子代理直读 41KB×50 的完整蒸馏，读料耗尽时间预算（1800s 墙）且上下文过载导致偷懒。原料包压到 ~1/4，保命题/概念/金句/反模式/总结五件套，100% 通读才可行。**蒸馏原文件永远是真相源，原料包随时可再生成。**

## Phase 0: 工作台三件套

```
~/workspace/<项目名>/
├── materials/           # 原料包 + 每章速览索引 index_NN.md
├── output/              # 成品章节（验收后归档）
│   └── parts/           # 超大章的 A/B 半章原件
├── themes.json          # 主题 → 书单映射
├── chapter_plan.json    # 章节 → {books, index路径}
├── progress.json        # 断点账本（状态机见下）
└── SUBAGENT_BRIEF.md    # 公共作业简报（模板: templates/integration-subagent-brief.md）
```

- 每主题速览索引用 `scripts/gen_index.py` 生成（从原料包解析命题+概念名，子代理先读它设计分篇结构，写作时再逐本读原料包）
- 100 本章 = A/B 两个半章任务（各 ~50 本），产出独立 parts 文件，父 agent 验收后用 `scripts/merge_parts.py` 合并（统一 H1、拼接正文、保留一份来源书目）

## Phase 1: 原料包抽取（脚本，非 subagent）

直接运行成品脚本：

```bash
python3 scripts/extract_materials.py <蒸馏拆解目录> <蒸馏MOC文件|none> <输出目录>
```

- 抽取五件套：命题（标题后首个 > 引用）→ 概念（### 节的 定义/机制/案例/启示，各截 110 字）→ 金句（金句集锦前 12 条）→ 反模式（表格前 10 行）→ 一句话总结；无概念节时兜底抽 ## 节脉络
- 自动产出 `materials_index.json`；MOC 与磁盘差集校验（ghost/orphan 双向报告）
- 大小基准：原料包中位 ≈ 原拆解的 1/4（629 本实测中位 9.1KB）；超一半偏差说明蒸馏五件套缺件，先修拆解再整合
- **验收**：原料包数 == 蒸馏文件数；抽查 3-5 份看结构完整

## Phase 2: 主题分类

- 有现成分类（如蒸馏 MOC 的分类节）→ 直接解析 MOC 标题行 `## 分类名（N）` + 书单行 `- [[书名-完整拆解]]`，与磁盘文件集做差集核对（两边都必须 0 缺口）
- 无现成分类的，关键词匹配分 8-15 主题，单主题 >50 本必须拆 A/B
- **分类是映射不是创作**：跟源数据的分类走，不要发明新分类

## Phase 3: 并行整合（delegate_task）

### 并发与节奏
- **按文件竞争域判断并发**：不同章节文件互不竞争，可 2 并发双轨（如 A 轨统稿 04 + B 轨深补 01 同时跑）；同一文件的多次加工必须串行
- 稳态 2 并发；上游过载期（429 波次活跃）降 1（串行：发一个→验收→再发下一个，用户拍板过此模式）
- 任务按书数从小到大排队（小章先跑 = 早期拿完成品 + 流程热身）
- 每个任务独立 delegation（失败互不拖累，僵尸不阻塞兄弟任务）

### 子代理任务指令必须包含
1. 简报路径（SUBAGENT_BRIEF.md，铁律全在里面，指令只发差异部分）
2. 该章 index 路径 + 原料包目录 + 产出路径
3. 章节结构要求（2-4 篇 × 4-6 小节 + 实践清单 + 来源书目）
4. **字符下限（明写「Unicode 字符，python len() 数」）**：≤20 本 ≥2 万；21-50 本 ≥3.5 万；≥41 本按 5 万（实战收紧线）
5. **时间策略**：读料与写作穿插，每读 10-15 本先写成型部分；收尾结构（清单+书目）尽早写上再补织入
6. A/B 拆半时明确「只负责本半书单」+ 主题切分角度（防撞车）

### SUBAGENT_BRIEF.md 必含铁律（实战验证版）
- **断点续写协议**（开工第一件事）：ls 产出——不存在→从零写；存在且无来源书目完结段→读尾部从断点追加；存在且完整→只核对不重写
- **读文件规矩**：中文大文件 read_file 可能误报 Binary，一律 python 分段读，100% 读完禁止抽样
- **密度铁律**：不节省篇幅；每本书 ≥1 处可辨认贡献；跨书共识合并标注、冲突并置不抹平；保留具体数字/框架/人名；不复制原料包原段
- **分段写入**：write_file 首段 ≤5KB，之后 python 追加（脚本名独占 /tmp/append_{章号}_{序号}.py），禁止 heredoc；每 2-3 段 wc 校验增长
- **字符口径**：下限一律指 Unicode 字符（len()），不是字节数（中文 UTF-8 每字 3 字节，subagent 会拿字节数交差）

## Phase 4: 验收（每章落地必跑，以磁盘为准）

直接运行成品脚本：

```bash
python3 scripts/qc_chapter.py <章节文件> <书单json> [--floor N]
```

- 五项一次跑完：字符数（len() 口径，下限自动按书数定档）/ 书名覆盖（**先去作者后缀再匹配**——`书名 - 作者` 文件名和嵌套书名号都会切断朴素正则）/ 偷懒词扫描（篇幅所限/不一一列举/此处略）/ 结构（## 篇章+实践清单+来源书目，重复 ## 标题检测）/ 收尾（尾部是来源书目完结段）
- 退出码 0=全过 1=有问题，可串进自动化

**铁律：subagent 报 timeout/429 ≠ 无产物。先跑磁盘 QC 再判定死活**——实测三次「任务失败但磁盘已完整」（死在汇报步）。
**铁律：验收后必查篇章编号连续性**（`## 第N篇` 按出现顺序一/二/三…）——统稿任务曾报告「已重排」但磁盘上 5/6 篇顺序颠倒且编号错位，子代理自述与磁盘不符时以磁盘为准、人眼复核编号。

## Phase 5: 合并与归档

- A/B 半章合并：`python3 scripts/merge_parts.py <A半章> <B半章> <输出> "<全章导语>"` ——自动剥 A 的来源书目段、剥 B 的 H1、统一标题，合并后用 `qc_chapter.py` 以 A+B 并集书单跑全章覆盖校验
- 归档：先备份旧版（挪到 `旧版-YYYYMM/` 子目录），新章落位，重写 MOC（章节表+导读+数据来源注明蒸馏代际）
- 断点账本 progress.json 记录全程状态，中断可续
- **清理**：归档后清工作台过程件，类型清单：原料包中转副本（如 10_src/）、各任务开工备份（*_pre_thicken.md / *_pre_uniform.md / _backup.md）、子代理中间账本（*_progress.json、digest 文件）、/tmp/append_*.py。保留：三账本（themes/chapter_plan/progress）+ master_plan + 简报 + output 成品副本；原料包可删（蒸馏是真相源，`extract_materials.py` 随时逐字节再生成），删前过目清单

## Phase 6: 二轮加工（初写完成后的可选深化，按需选用）

### 6a. 统稿 pass（A/B 拆半章必做）
硬拼接的两半由不同子代理独立写成，互相不知道对方内容，直接归档会有拼接痕迹。统稿任务指令要点：
- 通读全章 + 全部书单 → 删人为分隔线/拼接标题 → 篇章重排使主题推进连贯（给建议顺序但以书单实际构成为准）→ 篇间补过渡句
- 跨半章同主题小节互相呼应，重复论点合并；多个「实践清单」合并为一个（去重，25-30 条）；来源书目只留一份（**注意：合并件曾出现 A 半书目整段缺失的隐藏缺陷，统稿时核对书目数 == 总书数**）
- 铁律：覆盖数不得降、不删实质内容只重排合并、字符只增不减
- ⚠️ 子代理报告的篇章顺序可能与磁盘不符——验收时脚本核对编号连续性

### 6b. 密度深补（初写普遍只榨原料包一半）
实测初写密度 770-1,050 字符/本，深补后可达 1,300-1,700。判据：字符/本 < 1,100 的章值得深补。任务指令要点：
- 用「未覆盖率检测」（n-gram shingle 对比正文）锁定原料包中未吸收的框架细节/数字/案例/步骤/金句/反模式，织入对应小节
- 已经过一轮补厚的章，指令必须写「重点挖仍未被吸收的深层内容，不重复已有论点」（防注水）；每处插入锚定原句，锚点未命中（引号形态「」vs""差异）就重新定位，禁止跳过
- 目标密度参考：1,200-1,700 字符/本；深补幅度实测 +43%~+112%

### 6c. 专题切片（第二分类轴，按需立项）
从同一批原料包按另一主题轴拉书单生成专题章（如从旧版分类、或按人群/场景轴）。立项判据：
- 与主章书单重叠 <50%（重叠高的主题经主章可查，立了反而制造第二分类轴混乱）
- 书数 ≥8 本（太少撑不起一章）
- 导语必须说明「专题切片、与主章体系并存、部分书亦出现在主章」，MOC 分开两个区块
- 实测：20 个候选轴立项 4 个（育儿 13/社会系统 11/叙事文学 23/人际关系 20），否决 16 个

### 并发
统稿/深补/专题操作不同文件，可与其他轨 2 并发；同一章的多轮加工串行。

## 故障处置（实战 Playbook）

### HTTP 429
- **波形**：上游瞬时过载呈波次，25-43 分钟一波；与任务大小/并发无关（同批 16 本存活、5 本和 34 本挂掉）
- **冷失败**（<2 分钟死、磁盘无产物）：Hermes 内部只重试 3 次且集中 1 分钟，等=白等。冷却 3-5 分钟直接重派（terminal background sleep+notify 计时，不空转轮询）
- **热失败**（有半成品）：按断点续写协议续写
- **持续过载期**（连单任务也被灭）：降串行，发一个→验收→再发下一个；用户拍板过此模式

### 超时（child_timeout_seconds）
- 1800s 默认墙对 40+ 本「读料+写作」任务不够（读料就要 15-20 分钟）
- **建议 config.yaml `delegation.child_timeout_seconds: 0`（官方支持的关法，0/负数=禁用；防挂死由心跳+网关空闲超时兜底）**
- 改完即生效（派任务时现读），无需重启
- 任务指令加「读料与写作穿插」双保险

### 内容污染
- 并行临时脚本撞名 → 独占文件名 + 质检查 `###` 重复标题
- 半成品重写前先备份（parts/ 下存 _backup.md）
- A/B 半章合并后必须重跑全章 QC（A+B 并集覆盖 + 结构完整）

## 与拆书流程的衔接

```
epub/pdf → (book-distiller 主流程) → 蒸馏拆解 630 本
                                        ↓ 本工作流
                                    主题知识手册 12 章
```

- 拆书质量直接决定整合上限：蒸馏五件套齐全 → 原料包饱满；缺件 → 原料包对应层为空
- 整合不回写蒸馏：两代产物共存时，MOC 注明代际（「基于 2026-08 重拆蒸馏」），防「要不要重新整合」的反复追问
